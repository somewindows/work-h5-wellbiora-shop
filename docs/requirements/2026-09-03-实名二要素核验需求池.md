# 需求池：实名二要素核验（姓名 + 身份证号真伪校验）

- **录入日期**：2026-09-03
- **来源**：项目内部讨论（下单实名环节排障时提出）
- **状态**：🅿️ 需求池暂存，未排期（待与项目负责人确认后转入 TODO）
- **背景**：当前实名认证只做 18 位格式校验（`server/src/profile/profile.service.ts` 的 `saveRealname`），不验真伪；真正的终审在海关申报环节，退单会造成退款和客诉

---

## 一、需求描述

在下单/实名提交环节接入第三方「二要素核验」API（姓名 + 身份证号一致性比对），在订单推送给君梦/海关**之前**拦住虚假或错误的实名信息，降低海关退单率。

## 二、现状与目标

| | 现状 | 目标 |
|---|---|---|
| 校验时点 | 海关申报时才终审，退单后置 | 下单前预检拦截 |
| 校验能力 | 仅格式正则 | 姓名+身份证号与权威库比对 |
| 假信息后果 | 海关退单 → 自动退款、用户流失 | 当场提示用户修改 |

## 三、候选方案（评估时再细化）

- 阿里云 / 腾讯云「身份证二要素核验」API（按次计费，约 0.1~0.3 元/次）
- 公安一所 CTID 渠道（合规性强，接入门槛高）
- 微信生态内能力（如有）可顺带评估

## 四、注意点

- **合规**：身份证号属于敏感个人信息，送第三方核验需在隐私政策中明示并取得同意；传输全程 HTTPS，不留存核验通道的明文日志
- **成本**：按次计费，可考虑仅对「首次实名」或「修改实名」时核验，年度额度累计仍走本地 HMAC 指纹
- **降级**：核验服务不可用时要有兜底策略（放行 or 阻断，需业务决策）
- 不改变现有「实名 ≠ 注册」「身份证只存密文 + HMAC 指纹」的数据链路（见 `docs/tech/auth-and-account.md`）

## 五、预估工作量

服务端一个核验适配层 + 实名保存接口接入 + 前端错误提示，小工作量；主要成本在服务商选型、签约与合规文本更新。
