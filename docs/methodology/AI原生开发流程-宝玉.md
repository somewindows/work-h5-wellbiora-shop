## 一、核心认知：流程没变，角色变了

AI 原生开发**本质上还是传统软件开发流程**——可行性分析、方案设计、原型设计、编码实现、测试验证，一步不少。

变化的是**执行主体**：

- 以前：每个环节都是人亲手干。
- 现在：**人是指挥官，Agent 是执行者**。人只在关键路径上做确认和决策，具体分析、设计、编码、调试全部交给 Agent。
- 打个比方：你从一线程序员升级成了技术总监。你不再写每一行代码，但你要决定做不做、怎么做、做得对不对。

写代码反而是变化**最小**的环节——现在的大模型编码能力已经极好。真正有意思的变化在代码之外：需求怎么分析、方案怎么设计、原型怎么做、测试怎么跑。

## 二、五阶段流程详解

### 1. 可行性分析 —— 先决定要不要做

- **最容易被跳过、但最不该被跳过的一步。**「先决定要不要做，再去做。」
- 是期望值的赌注：大部分时候帮你避开弯路，偶尔也会看走眼（他自己做过一个本地文本模型拆分对齐的功能，可行性分析时觉得没问题，做完发现体验糟糕，砍掉，浪费几天 + 一堆 token）。但不做这一步，踩的坑只会更多。
- 两个层面：
  - **产品角度**：功能有没有价值？和产品定位是否匹配？
  - **技术角度**：技术上能不能做到？成本是否可控？
- 操作模式：**Agent 做分析和罗列方案，人做最终判断和拍板**。人不需要研究每个方案的细节，但需要基于产品判断和技术直觉做最终决策。

### 2. 设计文档 —— Agent 之间的桥梁

AI 时代文档有了全新角色：**人和 Agent 之间、Agent 和 Agent 之间的桥梁**。

- **文档是给人确认和修改的载体**：Agent 把方案写成文档，人通读、改方向、改细节。
- **文档是 Agent Session 之间传递上下文的媒介**：每个 Session 上下文有限，从「设计」进入「开发」往往是新 Session。没有文档，下一个 Session 就是从零开始。**文档是 AI 原生开发的「记忆载体」。**
- 理想状态：每个阶段结束都生成可留档的交付物（需求文档、设计方案、原型、代码、测试），结合 git 跟踪变更，交付物本身就是审计记录（谁提的需求、Agent 产出了什么、谁批准的）。
- 关键操作细节：**确认后的文档，就是下一个 Agent Session 的全部起点**。只需一句「按 docs/xxx.md 实现」。
- 他的自省：设计文档写完应该仔细审查，这个成本远低于写完代码再推翻。

### 3. 高精度原型设计 —— 需求、原型、UI 三合一

- 传统流程里需求/原型/UI 是三个独立步骤，由不同人完成，每次交接都有信息损耗。AI 加持下三者合并为一步：**高精度原型设计**——原型不是线框图，而是接近最终成品的高保真设计，直接包含交互逻辑和视觉设计。
- 工具：AI Agent + 好的 Design Skill（首推 Claude Design，也可用他的 baoyu-design：https://github.com/JimLiu/baoyu-design ，对话中说「原型设计」即可触发）。
- **原型阶段的修改成本很低，做成产品后再改成本很高**——这个阶段值得花时间反复打磨。他调整了好几轮：布局改 Tab、加服务状态图标、从设置页挪到主界面。

### 4. 实现

- 有了设计方案文档 + 原型（UI），让 AI 写代码对现在的 Agent 来说是很简单的事。
- 他的做法：配合 `/goal`，把文档一起发给 Agent 实施，Agent 按文档规划的 Milestones 逐个实现，还会自己截图验证结果。

### 5. 测试验证 —— 人当 QA

- Agent 会帮忙验证，但**不代表可以完全信赖**。人要自己手动跑几遍，把发现的问题喂给 Agent 调整，几轮下来就差不多可用了。
- 他没有 Review 代码——把自己当 QA，只做黑盒测试。（适用前提：个人项目 + 对所用模型的信任；团队/商业项目应视风险加码。）

## 三、要点速记

| 阶段 | 人的角色 | Agent 的角色 | 交付物 |
|---|---|---|---|
| 可行性分析 | 拍板做不做 | 分析、列方案 | 可行性结论 |
| 设计文档 | 审查、确认方向 | 起草文档 | 设计文档（留档） |
| 原型设计 | 反复提反馈 | 产出高保真原型 | 可交互原型 |
| 实现 | 盯 Milestone | 按文档编码、自验证 | 代码 |
| 测试验证 | 黑盒 QA | 修问题 | 可用功能 |

三条最贵的心得：

1. **先决定要不要做，再去做**（可行性分析是期望值赌注）。
2. **文档是 Session 的记忆载体**——确认后的文档 = 下一个 Session 的全部起点。
3. **原型期多改，产品期少改**——修改成本随阶段递增。

## 四、在本项目（WELLBIORA H5 商城）的落地对照

| 方法论 | 本项目实践 |
|---|---|
| 可行性分析 | 风险点不在「商城能不能做」，而在外部依赖（君梦 OMS 签名、微信支付+报关）；计划用 spike 脚本先行验证 |
| 文档做记忆载体 | `AGENTS.md`（长期上下文）+ `docs/tasks/TODO.md`（活跃任务）+ `archive/`（归档冷存储）+ 规划中的 `docs/tech/` 技术设计文档 |
| 高精度原型先行 | `prototype/app/` V2/V3 高保真原型（8 页全链路），baoyu-design skill 已 vendored 至 `.agents/skills/` |
| Milestone 实现 | 规划：M1 商品浏览（纯前端 mock）→ M2 购物车/下单 → M3 后端骨架 → M4 君梦/微信支付真联调 |
| 人当 QA | 黑盒验收 + 额外增加「文案合规红线」人工 checklist（保健品广告合规，Agent 不易自查） |

### 与原方法论的两点差异（项目特性决定）

1. **从零建工程，首版设计文档要更重**：目录结构、状态管理、内容块渲染器 type 定义一旦写歪，8 个页面全返工。
2. **多了一条合规主线**：文案红线（无医疗术语、数据宣称带脚注、合规声明面板）需纳入每轮 QA，这是纯工具类 App 没有的约束。
