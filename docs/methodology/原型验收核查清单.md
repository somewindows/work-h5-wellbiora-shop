# 原型验收核查清单（设计基线冻结前）

> 沉淀日期：2026-08-26。来源：H5 商城 T5 原型验收实战（8+1 页，三轮并行核查 + 7 项修复 + 补登录页）。
> 用途：以后任何「原型/页面定稿冻结」或「交付外部演示」前，按此清单过一遍。配合并行子代理核查效率最高（按页面域拆 2-3 组，每组带明确核查项）。

---

## 一、资源与部署（决定能不能直接上传演示）

- [ ] 所有图片/CSS/JS 引用为**相对路径**，无 `/assets/...` 开头的绝对路径（传服务器子目录会 404）
- [ ] 逐一核对引用的文件在磁盘上存在（引用存在性）；磁盘存在但零引用的文件可排除不上传
- [ ] 相对路径写法统一（`assets/x` vs `./assets/x` vs `../assets/x` 不混用）
- [ ] 外部演示前摘掉内部入口（本项目教训：V3 页留有「回看 V1」入口，外部人员会误入历史冻结版）

## 二、链路与导航

- [ ] 全页面 href / location.href 目标文件逐一核实存在，无死链、无未承接的空 `href="#"`
- [ ] 页面间跳转**传参对得上**（如订单列表 → 详情的订单号与 mock 数据匹配）
- [ ] 列表 → 详情 → 返回的链路闭环；tabbar 当前页用 `return false` 抑制自跳是惯例，不算死链
- [ ] 找不到数据时的兜底行为要明确（本项目教训：`findOrder` 静默回退第一条数据，排查极易误判）

## 三、业务规则的页面化（最容易漏的一类）

对照需求/技术文档里的**每一条硬规则**，问一句「用户在哪一页能看到/感知到它」：

- [ ] 硬校验类规则是否有对应 UI（本项目：单笔 5000 限额做了购物车拦截演示；年度 26000 只有文案——可以，但要在冻结口径里注明「由后端硬校验」）
- [ ] 状态机完整性：技术文档定义的状态映射，原型是否**全部可展示**（本项目教训：OMS 映射出「已取消」态，技术文档早记了「原型没有」，验收时才补；缺的状态会导致渲染 undefined）
- [ ] 操作的边界条件：某状态下**不能做**的事，有没有给用户出口（本项目教训：申报后不能自助取消，但页面连「引导人工客服」的提示都没有）
- [ ] 「暂不做的功能」入口要么没有、要么有承接（本项目教训：退款/售后入口点进去是空 toast 死胡同，应直接接客服弹层）
- [ ] 关键信息展示完整性（本项目教训：结算页漏了「微信支付」方式展示；订单详情漏了实名身份证脱敏——三单对碰的页面化体现）

## 四、合规红线（保健品/跨境行业专属，通用项目替换为自己的红线）

- [ ] 数据宣称带 `*` 的页面**逐页**查脚注（本项目教训：详情页有脚注，首页同一句宣称漏了）
- [ ] 高风险词 grep 兜底：治疗 / 预防 / 疗效 / 解毒 / Detox 等，命中逐个确认
- [ ] 固定合规模块（声明折叠面板）存在且不可删
- [ ] 收集个人信息的页面（登录、结算、实名）都有协议勾选 + 协议**有真实正文**，不是占位 toast

## 五、交互与工程健康

- [ ] 模式切换的完整性（本项目：购物车管理模式底部仍显示合计金额，易误导）
- [ ] 校验失败体验一致（标红 vs 仅 toast 不要混用）
- [ ] 静态 JS 体检：所有 on* handler 的函数有定义、getElementById 的 ID 存在、模板字符串配平（可写个 Python 脚本批量扫）
- [ ] 移动端三件套：viewport meta + `100dvh` 容器 + `env(safe-area-inset-bottom)` 底部栏

## 六、流程教训（本次验收元经验）

1. **技术文档里的"待办备注"要回查**：君梦对接笔记里写着「前端需补已取消态」，但原型收工时没人回去落实——验收清单必须包含「回查所有技术文档的待办备注」这一步。
2. **MVP 页面清单本身会漏页**：8 页清单没有登录页，直到验收讨论才暴露。页面清单冻结前要问「用户从哪进来、新用户第一步做什么」。
3. **核查按页面域并行拆给子代理**：购物车/结算/地址一组、订单/我的一组、商品/资源/合规一组，每组带编号清单，结论 + 文件:行号证据，比单线程逐页读快且不漏。
4. **修复后立即做机械抽查**（grep 关键标识 + handler/ID 配平），不等浏览器人工点验才发现问题。
