### R01 · 验证码错误次数被事务回滚

**成立。** `server/src/auth/mysql-sms-code.store.ts:59-83` 的 `verify()` 中，`record.attempts += 1`（`:75`）、第五次 `manager.remove`（`:77`）与抛异常（`:81`）全部在同一个 `dataSource.transaction` 回调（`:60-82`）内。已直接读取本仓 `node_modules/typeorm/entity-manager/EntityManager.js:73-86` 确认 rollback 语义，非推测。

**比原报告更严重**：原报告写"获得**超过**原定 5 次的在线猜测机会"，实际是**无限次**——计数永远归零，"第 5 次删除"也一并回滚，唯一失效条件是 5 分钟过期或猜中。且核实发现登录接口 `POST /api/v1/auth/login` **完全没有限流**（全仓无 `ThrottlerModule`/throttle guard），发码侧的 IP 限流对 `verify()` 无效。

**但仍同意"中危"定级**：6 位 CSPRNG 码空间 1e6、窗口 5 分钟、悲观写锁把请求串行化，实际枚举窗口内半个空间不现实。属"控制措施完全失效 + 实际可利用性受限"。

**测试为何没拦住**：`mysql-sms-code.store.spec.ts:23-25` 把事务 mock 成 `transaction: async (cb) => cb(manager)`，无回滚语义。原报告这一点判断准确。

内存路径 `MemorySmsCodeStore`（`sms-code.store.ts:44-58`）把计数存在 Map 里，**没有这个问题**——缺陷只在生产实际使用的 MySQL 路径上。

### R02 · 无 openid 时订单已创建却返回失败

**成立，且比原报告更严重。**

`server/src/orders/order.service.ts:73-84` 确认顺序：落库（`:80`）→ 存明细（`:81`）→ 逐条删购物车（`:82`）→ 记录事件（`:83`）→ 最后才取支付参数（`:84`）。全仓 grep `queryRunner|@Transactional|manager.transaction` 在 `src/orders/` 下**零命中**，无任何回滚。

抛错点 `wechat-payment.adapter.ts:45` 的 `if (!ctx?.openid) throw new BusinessException(40007, ...)` 位于方法第一条语句，**在调微信之前**，所以微信侧没留预支付单，但本地订单已落库。

**原报告写"首次用户"，实际是每个新用户首单必断**：前端唯一登录方式是手机号+验证码（`LoginView.vue:3`），微信静默授权只在支付路径触发。所以"无 openid 用户第一次下单"不是边缘场景，而是**所有用户的必经路径**。

重试链路同样确认：`CheckoutView.vue:77` 每次点击都 `genRequestId()` 生成新 UUID，而购物车已在 `:82` 被物理删除 → 第二次点击在第 209 行抛 `40003 请先选择要结算的商品`。

修复成本极低（把 `createPayParams` 移出 `create()`，或 catch 后仍返回 orderNo），属"高影响 + 易修"。

### R03 · 下单多步落库无原子性

**成立。** `order.repository.ts:84-89` 的 `createOrder` / `saveOrder` / `saveItems` / `recordStatusEvent` 各自 `Repository.save`，接口签名（`:38-53`）不接收 `EntityManager`，无事务参数。幂等分支 `order.service.ts:68-69` 只检查主单存在性，不校验明细完整性。`order.entity.ts:4` 的 `@Unique(['userId','requestId'])` 确实存在。

**同意原报告，但评级下调至中**：触发需要 DB 中途异常或进程被杀，窗口窄；且幂等重试返回既有主单在多数失败序列下反而起到恢复作用。真正难恢复的组合是"明细缺失 + 主单已 paid"。

补充一点原报告没说透的：`:82` 是 `for` 循环**逐条**删除购物车，使"部分清空"成为独立风险，而非整批成功/整批失败。

### R04 · 退款受理被标为已退款

**成立，引用精确。** `wechat-payment.adapter.ts:80-86` 确实声明了 `WechatRefundResponse.status` 却从不读取，只返回 `{ refundNo: result.out_refund_no }`。`admin-order.service.ts:189-192` 在微信返回后无条件写 `paymentStatus: 'refunded'`，并在 `:184` 立刻封死后续退款。

**独立退款单表确认不存在**：实体目录无退款实体，迁移清单无退款表，全库只有 `orders.refund_fen` / `refunded_at` 两个字段。仅有 mock 适配器 `local-payment.adapter.ts:43` 的内存数组（重启即丢）。

**根因在接口层**：`local-payment.adapter.ts:6-8` 的 `PaymentRefundResult` 只有 `refundNo` 一个字段，**结构上无法承载状态**。所以修适配器必须先改接口定义，不能只改实现。

另：`refundFen` 是覆盖写而非累加，即便将来放开多次退款也会丢历史。

### R05 · 退款号随机生成

**成立。** `wechat-payment.adapter.ts:78-79` 用 `randomUUID().slice(0,9)` 拼 `out_refund_no`，纯随机、无幂等键。服务层 `admin-order.service.ts:180-195` 是"读—判—调外部—写"四段式，无事务、无锁、无版本号、无唯一约束。

**同意原报告的自我设限**（它主动否认"可无限退款/退超原单金额"，与微信侧累计上限一致），这是负责任的收敛。

**但我认为真正的触发器被错放了**：原报告强调"两个并发请求"，实际更现实的是**网络超时/丢包后的重试**——适配器抛错时本地无任何落库痕迹（`:191` 的写入根本不执行），管理员重试即产生第二笔退款。这条路径**不需要并发，一次点击加一次重试即可**，且与 R12 的"无应用级超时（最长可阻塞约 5 分钟）"叠加后窗口可达数分钟。

### R06 · 预建待付款订单绕过年度限额

**成立，且原报告严重低估。**

额度校验**全仓只有一处**：`order.service.ts:223` 的 `sumDeclaredFen`（grep 确认唯一调用点），只在 `prepare()` 内，而 `prepare()` 仅被 `precheck()` 与 `create()` 调用。**支付登记路径 `handleWechatPaid`（`order.service.ts:113-138`）完全不查额度**——只做幂等、状态校验、金额比对、推仓落库四件事。旁路入口同样不查：`confirmMockPayment`、管理员补单。

汇总 SQL（`order.repository.ts:78-83`）确实只认 `paid_at IS NOT NULL`。

**原报告低估之处**：它只举了"25000 + 两笔 1000 = 27000"的例子，但代码对**待付款订单笔数没有任何上限**，也无预占/冻结。已有 25000 元时可先建**任意笔** 1000 元待付款单（每笔都不满足 `> 2600000`），再逐笔支付 → 累计**上不封顶**（仅受单笔 5000 元与微信侧限制）。最小演示才是 27000。

**另两点原报告未提**：① 汇总窗口用 `createdAt` 而非 `paid_at`，跨年订单会记到创建年份；② `prepare` 本身的检查是 check-then-act 非原子，无锁无条件更新，并发下单即可绕过。

**定级高的理由**：26000 元/人/年是跨境电商的**监管性**限额（AGENTS.md 硬性规则第 2 条），不是普通业务规则；无需特殊权限，普通登录用户即可触发；而支付回调是唯一可信的支付成功来源，防线正好架在最不该漏的一环。
