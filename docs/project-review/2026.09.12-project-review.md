## 二、P0：正式收款前优先修复

### R01 · 验证码输错次数在 MySQL 中被回滚【旧问题仍存在；安全】

- 证据：`server/src/auth/mysql-sms-code.store.ts:59–83`；匿名入口 `auth.controller.ts` 的 `login()`。
- 错误验证码在事务内增加 `attempts`，保存/删除后立即抛异常。事务回滚会撤销计数及第五次删除；下一次请求仍拿到旧计数。行锁只能串行化操作，不能使回滚的计数生效。
- 攻击前提：目标手机号存在尚未过期的验证码，攻击者能访问登录 API。攻击者获得超过原定 5 次的在线猜测机会；并非“任意验证码可登录”，仍受验证码有效期和请求吞吐限制。
- 安全评级：中危，源码置信度高；未进行生产爆破或真实 MySQL 复现。
- 修改方向：事务返回成功/失败结果，**提交失败次数后**在事务外抛业务异常；增加手机号及来源维度的验证限速。
- 验收：真实 MySQL 连续输错后检查持久化计数，第五次后旧验证码不能使用；并验证正确验证码只能消费一次。只 mock `transaction(callback)` 的单测不足以覆盖回滚。

### R02 · 首次没有 openid 时，订单已创建却向结算页返回失败【新增真实支付缺陷】

- 证据：`server/src/orders/order.service.ts:67–85`；`wechat-payment.adapter.ts:44–46`；`frontend/src/views/CheckoutView.vue:80–88`。
- 后端先写订单和明细、删除购物车，再获取 JSAPI 参数。首次用户尚未绑定 openid 时最后一步抛 `40007`，整个创建接口只返回错误，没有返回已创建的订单号。
- 结算页只 toast“下单失败”，不会进入负责 OAuth 的订单页；重试又生成新的 `requestId`，且服务端购物车已经清空。用户要自行去订单列表找待付款订单才能继续，正常首单流程中断。当前 e2e 先绑定 openid，再创建订单，绕开了该场景。
- 修改方向：分离“创建订单”和“获取支付参数”；本地订单提交成功就返回可恢复的订单号，进入订单页后再授权/调支付。同一次结算重试复用稳定幂等键。
- 验收：新手机号、无 openid、真实支付适配器模式，从购物车一遍完成授权与支付；模拟 JSAPI 超时仍能找到唯一订单。

### R03 · 下单多步落库没有原子性，失败后幂等返回不完整订单【旧问题仍存在】

- 证据：`order.service.ts:69–85`；`server/src/orders/order.repository.ts:64–89`；`order.entity.ts:4`。
- 主单、明细、逐条购物车删除、事件记录各自提交；中途异常可留下空明细订单、部分清空购物车或缺失事件。同请求号重试直接返回已有主单，没有检查其是否完整。
- 已有 `(userId, requestId)` 唯一约束是有效保护，但不能替代业务事务；并发同请求号仍可能收到唯一键错误，而不是一致的幂等响应。
- 修改方向：本地写操作放同一 MySQL 事务；并发唯一键冲突后读取已提交的同一结果；外部支付调用放事务之外。
- 验收：在每个落库步骤注入失败，结果必须全回滚或可恢复；并发同一幂等键只生成一套订单明细。

### R04 · 退款“受理”被标为“已退款”，部分退款也变全额终态【旧问题在真实通道中落实】

- 证据：`wechat-payment.adapter.ts:76–86` 丢弃微信返回 `status`；`admin-order.service.ts:162–170、180–194` 直接保存 `refunded`；`order.service.ts:141–159`；后台 `OrderDetailView.vue:112–113` 显示“退款成功”。
- 微信受理可以返回 `PROCESSING`，并非已到账。后续 `ABNORMAL/CLOSED` 通知只记录事件，订单仍为已退款；例如 100 元订单退款 1 元，也立刻禁止后续正常退款。
- 回调没有匹配持久化的退款单和退款金额；若退款从商户平台发起并有通知到达，本地也缺少完整退款账本来正确归集。正常后台路径提前置终态，还会跳过成功回调的事件分支。
- 修改方向：独立退款单，保存申请金额、微信退款 ID、状态、成功时间；退款受理只置“处理中”，最终以通知/查退款结果收敛；订单展示累计成功退款及剩余额度。[微信官方退款状态说明](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)
- 验收：覆盖 `PROCESSING→SUCCESS/ABNORMAL/CLOSED`、部分退款后再次退款、重复通知、商户平台退款对账。

### R05 · 退款号每次随机生成，重试和并发不能保证一次业务只退一次【旧问题仍存在】

- 证据：`wechat-payment.adapter.ts:79`；`admin-order.service.ts:180–195`；取消已支付订单也调用同一退款方法。
- 两次并发操作均可在本地“未退款”时通过；微信受理后本地写入失败，重试又生成新的 `out_refund_no`。部分退款时可能累计退超过本次运营原本想退的金额；本地 `refundFen` 还可能仅留下最后一笔。
- 反证与边界：入口有管理员鉴权和确认；不能描述成匿名用户可退款。微信有累计退款上限，**不能据此声称可无限退款或退超原单金额**。
- 修改方向：发起请求前持久化稳定退款单号，以该号重试；事务/锁控制剩余可退金额，失败后优先按原退款号查询，禁止凭网络错误创建新退款号。
- 验收：同一退款意图重复点击、并发提交、请求超时、本地写失败重试，均只出现一笔对应退款。

### R06 · 预建多笔待付款订单即可绕过商城年度限额【旧问题明确化；业务规则安全】

- 证据：`order.service.ts:208–225` 只在创建/预检检查；`order.repository.ts:78–82` 仅汇总 `paid_at IS NOT NULL`；支付登记 `order.service.ts:117–137` 不再检查额度。
- 不需要并发：年度已有 25000 元时，先依次创建两笔 1000 元待付款订单，两笔都按 25000 元校验通过，随后依次支付，商城累计变为 27000 元。
- 安全评级：中危，源码置信度高；影响是绕过项目明确要求的本地限额，**并不证明海关会放行超额订单**。外部海关额度查询也尚未接通。
- 修改方向：按实名指纹进行额度预占及原子扣减，取消/过期释放；支付、申报和退款建立一致的额度状态。年度归属按明确的业务时点设计，目前查询按创建年筛选，却只判断支付时间是否非空，跨年支付也有偏差。
- 验收：顺序预建多单、并发支付、跨年支付、不同账号同证件、关闭/退款释放，以及海关额度不足的补偿。

### R07 · 真实收款与 mock 仓储/身份放行没有隔离【旧问题仍存在】

- 证据：`server/src/orders/orders.module.ts:46` 始终绑定 `LocalWarehouseAdapter`；`server/src/orders/local-warehouse.adapter.ts` 只查商品上架状态、用内存记录推仓；`profile.service.ts:81–106`；`order.service.ts` 的 `handleWechatPaid()` 与报关方法。
- 当前真实支付成功可直接变为 `ship/local-accepted`，但没有真实库存数量、预占、OMS 订单、物流信息。重启后 mock 仓库记录消失。付款后页面却宣称“订单已提交海关申报”。
- 实名只验证字符串格式，留空身份证还可改姓名；`DIFFERENT` 仅 warn，没有拦截履约状态。报关未启用则直接跳过，实际不能宣称三单一致已核验。
- `LOCAL_TEST_MODE=1` 在 production 仍会启用内存仓储；微信全量配置缺失仍回落 mock。当前生产 `SMS_DEV_CONSOLE=1` 是 TODO 记载的联调开关，移除后如果没有真实短信适配器，会变为“短信服务尚未配置”，不是自动接入短信。
- 修改方向：增加明确的交易开放开关及生产启动约束；在真实仓储、库存、实名/三单核验和补偿闭环满足前限制为内部联调。将“已填写身份信息”“核验通过”“已申报”“仓库已接受”分开表达。
- 验收：生产误设测试模式应拒绝启动；缺通道配置不能开放收款；身份不一致必须阻止进入可发货状态。君梦接入坚持**测试环境先行、签名调试，并确认 `orderDeclaNo` 与 `plaformCode`（文档原始拼写）等参数**。

## 三、P1：支付和运营可靠性

### R08 · 用 `payer_total` 校验订单总额，优惠支付会被拒绝登记【新增；回调与补单都受影响】

- 证据：`payment-notify.controller.ts:69`；新增 `wechat-payment.adapter.ts:96`；`order.service.ts:124–127`。
- 两个入口都优先把用户实付 `payer_total` 与本地订单 `totalFen` 相比。使用代金券时 `payer_total` 可以小于订单总金额 `total`，正常成功支付因此被拒；手动补单复用了同一个错误，无法救回该场景。
- 修改方向：订单总额校验使用 `amount.total`；用户实付、优惠额独立保存用于财务明细，同时核验币种和交易身份字段。不要删除金额校验。[微信官方查单字段说明](https://pay.wechatpay.cn/doc/v3/merchant/4012791858)
- 验收：`total=10000,payer_total=9900` 的合法支付，通知与查单均可登记，错误 `total` 仍拒绝。本次没有证据表明原 0.01 元订单使用优惠，故不作为原故障根因。

### R09 · 取消没有关闭微信交易，迟到的成功支付无法登记【新增真实支付风险】

- 证据：`order.service.ts:97–104、117–122`；`admin-order.service.ts:158–160`；`local-payment.adapter.ts:26–32` 没有关闭交易能力。
- 用户拿到预支付参数后取消本地订单，微信交易仍可能成功；迟到通知看到本地已取消直接拒绝。新补单入口也复用这一拒绝逻辑，不能恢复“已取消但实际已扣款”的订单。
- 并发取消/回调还会按各自读到的旧对象保存，缺少条件更新，可能互相覆盖状态。
- 修改方向：查单/关单与本地取消状态机协调；收到真实扣款时必须保存支付事实，即使业务订单已取消，也应进入退款/人工异常队列。支付和取消使用条件更新及版本控制。
- 验收：已获取支付参数再取消、支付成功通知迟到、取消与通知并发、关单超时；不得留下微信有款而本地不可对账的状态。

### R10 · 支付落库与推仓/报关耦合，失败后“重推”并不完整【旧问题的新增支付表现】

- 证据：`order.service.ts:120、129–137、169–190`。
- 先推仓再保存支付：未来真实仓库故障会阻塞支付记账；推仓成功后数据库失败会在重试时重复推仓。当前 mock 推仓本身很简单，不能把真实仓库故障说成这次线上根因。
- 已保存 `paid` 后，事件/报关失败，下一次通知或补单会因已支付提前返回，无法补齐副作用。注释“待重推”没有对应持久化任务及重试入口；报关网络调用还被 `await`，只捕获异常不等于响应不阻塞。
- 修改方向：本地事务先确认支付及待处理任务，再异步推仓/报关；任务按订单/操作幂等、超时重试、持久化错误和人工恢复入口。保留管理员主动查单，补充自动对账，而不是重新实现一套支付状态更新。
- 验收：重复通知、并发通知、支付保存后宕机、推仓/报关超时、进程重启后任务恢复。

### R11 · 匿名伪造通知可触发证书下载放大【证书模式仍存在；安全】

- 证据：`payment-notify.controller.ts:111–120`；`wechat-pay.client.ts` 的 `verifyNotification()`、`refreshPlatformCertificates()` 与 `request()`。
- **仅在未配置公钥、走平台证书分支时**：攻击者不必有正确签名，只要带四个非空头及当前时间戳，未知 serial 或验签失败都会触发一次带商户签名的 `/v3/certificates` 请求；没有刷新合并、刷新间隔或应用级请求超时。公开回调入口没有对应限速。每次通知最多触发一次刷新，是资源成本放大，不是单请求扇出多次下载。
- 下午新增公钥分支直接本地验签或拒绝，不走下载逻辑；正确启用公钥的部署不受这一证书下载路径影响，不能继续把它列作该部署必然存在的风险。
- 安全评级：中危，源码置信度高。可放大外部请求、日志和连接负担并争抢真实回调资源；未进行负载攻击，不能声称已证明可打垮微信平台。固定请求域名意味着这**不是 SSRF**。
- 修改方向：缓存刷新 single-flight、最小刷新间隔及失败退避；已知证书签名错误不无限刷新；合理超时及入口资源限制，保证真实通知仍能重试成功。
- 验收：一批并发非法通知只触发受控次数的证书刷新；合法证书轮换能正常恢复。

### R12 · 公钥模式已支持，外部响应验签仍待补齐【部分已修；加固】

- `wechat-pay.config.ts` 已支持 `WXPAY_PUBLIC_KEY_PATH`/`WXPAY_PUBLIC_KEY_ID`；`wechat-pay.client.ts` 已对通知 serial 精确匹配后使用对应本地公钥验签。公钥适配缺口已修，生产配置与新单自动回调另行验收。
- `wechat-pay.client.ts` 的 `request()` 对成功 HTTP 响应直接 JSON 解析，没有微信响应签名验证；新增 `Wechatpay-Serial` 请求头并不等于验证响应签名。主动查单把该响应作为补记资金状态的依据。HTTPS 仍提供传输保护，因此不将此描述成普通外网攻击者可以伪造付款。
- 建议：统一请求/响应/通知的验证策略，核对 `appid/mchid/out_trade_no/transaction_id/currency` 等关联字段，严格处理缺失字段，支持证书轮换与公钥配置；增加网络超时。当前回调核心 RSA 验签及 AES-GCM 解密本身未发现可直接绕过的源码证据。

### R13 · 前端把 JSAPI 成功当成数据库已更新，只有一次刷新【新增体验缺陷】

- 证据：`frontend/src/composables/useWechatPay.ts` 的 JSAPI 成功分支；`OrderDetailView.vue` 与 `OrdersView.vue` 的支付完成回调。
- JSAPI 返回成功时通知可能尚未处理完，页面立即读取一次仍得到 `pay`；之后不再轮询，所以即使后台稍后变为已支付，当前页面仍可能显示待付款。这与“数据库实际没改”是两个不同问题。
- 修改方向：显示“支付结果确认中”，有限退避轮询服务端；刷新/返回前台时更新；超时保留查询入口，不凭 JSAPI 返回直接修改订单为已支付。防止重复点击再次发起支付。
- 授权失败也需停止自动续付：`handleAuthCallback()` 捕获绑定失败后仍返回待付订单号，页面再次 `payOrder→40007→OAuth`，持续失败时可能反复跳转。应仅在绑定成功后续付，错误允许用户明确重试。
- 验收：通知延迟数秒、通知失败、授权持续失败、网络断开后返回页面。

### R14 · H5 与后端订单状态不一致，收货/完成后页面可能空白或报错【跨端契约缺陷】

### R15 · 商品自动编号存在并发重号/覆盖风险，内容发布竞态未修【新旧并存】

- 新增编号风险：`server/src/admin/admin-catalog.service.ts:37–40` 先查最小空号，`server/src/catalog/catalog.repository.ts:138–140、154–155` 再 `save()`。两个创建请求可拿到相同 ID；如果后一个 save 查询时前一个已提交，ORM save 可按已有主键更新，覆盖先创建商品；另一些交错会报唯一键冲突。内存版则直接 `Map.set()` 覆盖。
- 修改方向：保留用户要求的“最小空闲编号可复用”规则，使用数据库并发安全分配及只插入语义，冲突重新分配；不要直接改成不可回收编号而改变业务规则。

### R16 · 反向代理下所有客户共用登录限流 IP【旧问题；安全/可用性】

- 证据：`server/src/main.ts:15–33` 未配置可信代理；短信 `auth.controller.ts:16` 使用 `@Ip()`；`admin-auth.service.ts:44` 使用 `ip:` 限流键；部署指南 Nginx 反代至本机并转发 X-Forwarded-For。
- 在文档部署拓扑下，请求 IP 会是 Nginx 的本机地址。少量失败后台登录可消耗所有后台访问者的同一 IP 额度；10 次发码可消耗所有消费者的同一短信来源窗口。攻击者无需管理员账号即可影响他人登录可用性。生产是否另有网关防护未核实。
- 安全评级：中危，代码与文档部署条件下置信度高。
- 修改方向：只信任实际本机 Nginx/已知代理链，限制后端监听和防火墙；正确取客户端 IP。不要直接 `trust proxy=true` 信任任意来源的伪造转发头。
- 验收：两个不同客户端独立计数；直接请求后端/伪造 XFF 不可随意改变可信身份。

### R17 · 自动备份已有脚本，但 Windows PowerShell 重定向可能生成不可直接恢复的 SQL【旧问题部分改善，仍需修】

- 证据：`server/scripts/backup.ps1:2、31`，任务调用 `powershell`，导出使用 `> $sqlFile`；部署指南 17.3。
- 旧报告所述“把 > 直接交给 mysqldump 参数”已通过脚本方式改善；现在是 shell 实际解释重定向。但 Windows PowerShell 5.1 的重定向会经过文本编码转换，常产生 UTF-16，MySQL 官方明确建议改用 `--result-file`。压缩成功、文件大于 1KB 都不能证明可恢复。[MySQL 官方说明](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)
- 修改方向：让 mysqldump 自己写 `--result-file`；保留脚本已有的退出码检查；在空库执行恢复并校验中文、表数量及订单/用户关联。编码不兼容不等于数据必然永久不可恢复，但不能把转码补救当作合格备份验收。数据库和身份证加密密钥需要独立、安全、可恢复的备份；不要将真实密钥写进报告或仓库。
- 验收：使用生产同版本 PowerShell/MySQL 执行一次导出→解压→空库恢复。本次未执行实际备份/恢复。
