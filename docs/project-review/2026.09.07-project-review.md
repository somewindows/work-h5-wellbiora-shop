# WELLBIORA 商城项目审查报告

> 审查日期：2026-09-07  
> 审查范围：`server/`、`frontend/`、`admin/`、部署文档、依赖与自动化测试。  
> 说明：本审查未修改业务代码、未连接生产数据库、未对线上环境进行攻击测试。

## 管理结论

项目已有清晰的 Vue 3 / NestJS / MySQL 分层架构，H5、后台和本地下单链路均已具备可演示的 MVP 形态。代码的模块边界、金额处理、加密存储、审计和输入校验总体方向正确，适合在当前基础上继续迭代。

但项目尚不具备开放真实交易的条件。支付、仓储仍是本地 mock；下单、退款、库存、额度与外部回调的生产级一致性尚未建立；另发现验证码错误次数限制在真实 MySQL 事务中失效的明确安全缺陷。建议当前定位为“内部验收与联调准备”，完成本文 P0/P1 后再评估收款上线。

| 维度 | 结论 |
| --- | --- |
| 技术架构 | 合理，当前规模无须重构 |
| 代码组织 | 模块划分清楚，已有接口抽象和测试 |
| 安全基础 | 已有加密、鉴权、限频；仍有实际缺陷需修复 |
| 交易可靠性 | 主要满足本地联调，尚未达到生产级 |
| 产品完成度 | 页面主体完整；支付、实名、客服、协议仍有待接入或演示环节 |
| 上线建议 | 可继续内部验收，暂不建议开放真实交易 |

## P0：上线前必须处理

### 1. 验证码错误次数在 MySQL 模式失效

- 位置：`server/src/auth/mysql-sms-code.store.ts`
- 现象：验证错误时先更新 `attempts`，再在同一事务中抛出异常。TypeORM 遇到异常会回滚事务，错误计数也随之回滚。
- 后果：原设计的“连续输错 5 次后验证码失效”无法生效，攻击者可在验证码有效期内持续猜测。
- 建议：将“更新错误次数”和“返回验证失败”改为可提交的流程；补真实 MySQL 集成测试，连续输错 5 次后确认记录被删除或锁定。

现有单测模拟了事务回调，但未模拟回滚，因此未覆盖该问题。

### 2. 下单没有完整数据库事务

- 位置：`server/src/orders/order.service.ts`
- 现象：订单主表、订单明细、购物车清理和状态事件分步保存。
- 后果：某一步失败可留下不完整订单；相同请求重试会返回该异常订单。前端每次重试又会生成新的 `requestId`，进一步削弱幂等保护。
- 建议：将本地订单落库、明细、购物车清理、状态事件放入同一事务；同一次结算重试复用请求号；补数据库失败和并发下单测试。

### 3. 退款缺少资金幂等与并发保护

- 位置：`server/src/orders/admin-order.service.ts`
- 现象：两个并发退款请求可同时通过“尚未退款”的判断；支付退款成功后，本地状态保存失败会导致重试再次退款；部分退款后直接标记为 `refunded`。
- 后果：真实支付接入后存在重复退款、账实不一致和无法处理剩余退款的风险。
- 建议：增加独立退款单，使用稳定退款请求号；维护“处理中 / 部分退款 / 全部退款”和累计退款金额；以支付查询或回调确认最终结果。

### 4. 生产环境没有完全隔离本地测试能力

- 位置：`server/src/common/runtime-mode.ts`、`server/src/orders/orders.module.ts`
- 风险：误设 `LOCAL_TEST_MODE=1` 可启用内存仓储和控制台验证码；支付与仓库当前无论环境如何都绑定本地 mock。
- 建议：生产启动时明确拒绝测试模式；未配置真实短信、支付、仓储适配器时关闭交易入口并报错；拒绝示例密钥与弱配置。

### 5. 依赖漏洞

- H5 生产依赖审计发现 Swiper 严重级原型污染漏洞，受影响范围为 `>=6.5.1, <12.1.2`；当前锁定版本为 11.x。
- 后端生产依赖审计发现 `qs` 中危漏洞，可修复。
- 建议：确认 Swiper 未被实际使用后删除；如仍需使用，升级至至少 12.1.2 并完成组件兼容验证。更新后端锁文件并重新执行审计。

## P1：真实交易联调前处理

### 实名、三单与年度额度

- 当前身份证仅做格式校验，页面的“已认证”实际是“已填写实名信息”。
- 已有证件时可保留旧身份证号并改姓名。
- 下单仅校验收货人姓名与保存的实名姓名一致，尚未校验真实支付人。
- 年度额度仅汇总本商城已支付订单；并发订单及外部海关累计额度待真实对接闭环。
- 库存检查目前只检查商品是否上架，没有数量库存和预占。

建议明确“信息已填写”和“身份已核验”的产品文案差异；支付接入时完成支付人核验；在支付、库存、海关申报链路中建立预占、补偿和最终结果校验。

### 仓库、支付与内容发布并发

- 仓库同步可将本地较新状态覆盖为旧状态，除已取消订单外缺少状态倒退保护。
- 内容发布是多步读写操作；两名管理员同时发布时可能出现校验对象与发布对象不一致、历史版本冲突。

建议定义严格状态机，只允许合法单向转换；发布以已校验快照和版本号为条件，并将发布、历史和审计操作事务化。

### 登录与部署

- 管理后台复用用户 JWT 配置，有效期为 7 天，尚无服务端撤销机制。
- Nginx 已转发 `X-Forwarded-For`，但应用未配置可信代理，短信与管理员登录的 IP 限流可能都识别为代理 IP。
- HTTPS 被安排为后续步骤；在收集登录、身份证或接入支付前应先启用。
- 全局异常响应不会暴露内部堆栈，这是正确的；但还应记录结构化错误日志和关联请求 ID，支持故障追查。
- 部署文档的 Windows 任务计划程序示例把 `>` 放进 `mysqldump.exe` 参数，重定向不会由该程序解释，备份文件可能不会生成。

建议管理员独立 JWT 密钥与更短会话期，增加撤销机制；只信任本机 Nginx 代理；使用 `--result-file` 或受限目录内的备份脚本；实际演练“备份后恢复至空库”。密钥需独立安全备份，否则恢复数据库后仍可能无法解密身份证数据。

## P2：体验与维护性改进

- 真实模式发送验证码成功后，H5 仍提示“mock 阶段任意 6 位可登录”。
- 客服“复制”仅显示演示提示；协议正文入口仍有占位提示。
- 结算页预检后不采用服务端返回金额，运营改价时展示金额与订单金额可能不一致。
- H5 对 401 已能识别，但未统一清除失效登录态并跳转登录页。
- 管理端商品列表先取全量再内存分页，当前仅 4 款商品影响很小；商品规模增长后改为数据库过滤、排序和分页。
- 建议逐步统一前后端订单状态、内容块等重复类型；将较长的页面组件拆分，降低维护成本。

## 已具备的良好实践

- Controller、Service、Repository 分层明确，支付和仓库已通过适配器接口隔离。
- 金额统一使用分；下单时服务端重新读取商品价格与上下架状态。
- 用户订单、地址查询均按用户归属限制，具备基础越权防护。
- 身份证号使用随机 IV 的 AES-256-GCM 加密保存，并以 HMAC 指纹用于年度额度查询。
- 管理员密码采用加盐 scrypt，比较使用恒定时间函数。
- 使用全局输入校验、统一 API 响应、内容块校验、操作审计和后台危险操作二次确认。

## 推荐执行顺序

1. 修复验证码计数缺陷；隔离生产/测试模式；升级或删除有漏洞依赖；启用 HTTPS、可信代理和可恢复备份。
2. 实现下单事务、库存预占与额度并发控制；建立支付回调、退款单与资金对账；完成仓库状态机和补偿任务。
3. 使用真实 MySQL、微信支付 sandbox、君梦测试环境完成异常路径联调。君梦接入须先做签名调试，并确认 `orderDeclaNo` 与文档原始拼写 `plaformCode`。
4. 补齐客服、协议、失效登录和金额展示，再进行 H5 与后台逐页人工视觉验收。

## 建议的“完成”验收标准

后续不应仅以“页面可点击、正常路径可走通”作为完成标准。下单、支付和退款须覆盖重复点击、网络超时、第三方延迟、数据库失败、并发请求和服务重启后的恢复场景，并保证订单、库存、资金与审计记录保持一致。
