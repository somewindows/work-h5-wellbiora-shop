# 2026-09-12 微信支付金额口径避坑

> 读者：改动支付金额校验、对账、退款金额相关代码的 agent。
> 每条 = 规则 + 出处（真实踩坑）。同目录《2026-09-12-微信支付联调避坑.md》是主清单，本文件专记金额口径。

## amount.total vs amount.payer_total

- **金额校验一律用 `amount.total`（订单总金额），绝不用 `amount.payer_total`（用户实付）**：用户使用微信支付优惠/代金券时 `payer_total < total`，按实付校验会把正常回调误判为金额不符而拒绝，微信按节奏重推约 24h、订单卡死。出处：T13 复审 R08（`order.service.ts` handleWechatPaid 原本用 payer_total 比对订单总额）。
- 回调 JSON、查单接口的 `amount` 对象同此口径：`total` = 商户订单总金额（应等于本地 `totalFen`），`payer_total` = 用户实际支付金额（含优惠减免后）。
- `payer_total` 与 `total` 不一致时**只告警不拒绝**（已固化为 logger.warn），但它意味着发生了营销减免，财务对账要留意。
- **遗留**：当前 payer_total 不落库、currency 字段未核验，正式收款前需补持久化实付金额 + 币种核验（TODO T13 第 2 批遗留项）。

## 取消订单后的扣款登记

- 已取消订单收到迟到支付回调时，**必须登记支付事实**（paymentStatus=paid + 交易单号 + 告警），不能整体拒绝：钱已在微信侧，本地无痕则后台人工退款入口被「订单未支付」校验挡死，资金对不上。出处：T13 复审 R09（修复后见 handleWechatPaid cancelled 分支）。
- 登记事实 ≠ 履约：cancelled 分支**不推仓、不报关**，写 systemRemark 提示人工退款（注意：这会让后台列表误显「海关拦截」红标，已知语义撞车，待拆字段）。
- 本地取消订单时应 best-effort 调微信关单接口（`/v3/pay/transactions/out-trade-no/{out_trade_no}/close`），关单失败只告警不阻断取消——关单只是降低迟到扣款概率，取消本身必须生效。

## 退款（R04/R05，2026-09-13 退款状态机落地后生效）

- **受理 ≠ 到账**：微信退款接口返回 `PROCESSING` 只是受理，资金 T+N 才到。退款终态只能由退款回调或 `queryRefund` 查单结果收敛（`SUCCESS`），禁止据受理响应直接置「已退款」。`ABNORMAL/CLOSED` 要记录并告警人工跟进。
- **退款单号（out_refund_no）发起前落库、终身复用**：同一退款意图的重试/重复点击/并发必须收敛到同一个退款单号——微信对同号重发幂等。**禁止凭网络错误换新号重发**（可能双重退款）；网络异常后先按原单号查 `/v3/refund/domestic/refunds/{out_refund_no}`，确认 404 未受理才允许置 failed 换新号。
- 同一订单同时只允许一笔在途退款；金额口径 = 剩余可退（实付 - 已到账 - 在途占用），部分退款后可再退剩余。
- 商户平台直接发起的退款会以回调形式到达，本地无单时按 `channel=platform` 补登（回调缺 `amount.refund` 时按 0 补登并标注「金额待人工核对」）。
- 订单支付状态由退款账本重算：全额到账=refunded / 有在途=refunding / 部分到账无在途=paid；**已 refunded 的订单账本重算不足额时拒绝降级**（防旧数据复活二次退款）。
- 取消已支付订单：退款校验/发起必须先于仓储撤单，否则校验失败会留下「仓储已撤、本地未取消」的夹缝态。
