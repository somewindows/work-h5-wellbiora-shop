# 君梦 OMS 对接注意事项（H5-shop）

> 基于 `docs/vendor/junmeng/`（君梦 OpenAPI 2.0 已拆分 Markdown）通读整理，2026-08-26。
> 本文是**我方视角的风险与决策清单**，接口字段细节一律回查 `docs/vendor/junmeng/api/` 单个文件，不在此复制。
> 写作目的：T6 技术设计文档（order-flow / oms-adapter）的输入；联调前的坑位预警。

## 一、签名与接入

1. **业务参数 `params` 不参与签名**——只签 `appId / method / timestamp` 三个公共参数（去掉 sign 和 params 后按 key 排序拼 `k=v&`，末尾追加 appSecret，MD5 转大写）。
   - 好处：签名实现极简，不存在中文/嵌套对象的序列化歧义。
   - 注意：业务体无签名保护，安全完全依赖 HTTPS + appSecret 保密（appSecret 只存服务端，硬规则 1）。
2. `timestamp` 为**毫秒时间戳字符串**，有效期 5 分钟 → 服务器必须 NTP 对时；任何重试都要重新生成 timestamp 和 sign，不能复用。
3. **文档笔误照单全收，不要"纠正"**：
   - `plaformCode`（platform 少个 t）、返回里的 `thridNo`（third 拼错）——代码里必须用原始拼写。
   - 下单接口文档里 method 示例值误写为 `jm.two.store.in.trade.get`，实际用 `jm.order.bonded.add`。
4. 生产环境 URL 含占位符 `#server/#mechanism`（要到君梦客户端开放平台获取）→ 说明存在多节点/机构码，**环境地址做成配置项**，别写死。
5. 测试环境路径是 `/test/test/api/...`（双 test），照抄别"优化"。
6. `logId` 返回字段「目前暂不支持」→ 排障靠自己：**后端必须落每次调用的请求/响应日志**（sign 前的拼接串可记录，appSecret 脱敏）。

## 二、下单（jm.order.bonded.add）—— 核心风险区

7. **金额单位全是分**：`disCount`、`frightFee`、`goods[].total`。且 `goods[].total` 口径是**「（税 + 商品金额）× 数量」的单品含税含优惠总额**，不是单价。计算口径必须写进 order-flow 文档，前后端统一。
8. **字段废弃但标必填**：`orderNo` 标了「弃用」却仍标 Y——实际传不传/传空，待联调确认（先按「batchNo 传真实单号、orderNo 同步传同值兜底」试）。
9. **支付先行**：`orderCustoms` 要求 `idcard + idcardName + payId + payNo`（支付单号）→ 必须先完成微信支付拿到支付单号，再推单给 OMS。下单时序：微信支付成功回调 → 推 OMS → 海关三单对碰。payId 用财付通备案号 `4403169D3W`。
10. **平台编码 `plaformCode`**：自建 H5 商城用哪个海关编码待确认（详见下方待确认清单）。注意数据矛盾：接入指南示例写「有赞 3301961SWG」，而 `reference/电商平台.md` 里有赞是「杭州起码科技有限公司 3301961H10」——两个值不一致，正好一起问。
11. **SKU 映射**：`goods_no` 是「商品在仓库的编码，请联系仓库商务」→ 我方数据库要维护「商城 SKU ↔ 仓库 goods_no」映射表，别把仓库编码直接当前台 SKU 用。
12. 效期/批次：`goodsType` 1=效期下单 2=批次下单；下单可指定 `expire`/`production`，默认先进先出。初期不指定，走 FIFO。
13. **取消有硬边界**：`jm.order.bonded.cancel` 仅限「未申报清单」的订单；已申报的只能联系仓库线下取消 → 产品设计：用户自助取消仅在申报前开放，申报后引导人工客服。**这直接决定订单状态机的可取消窗口**。

## 三、状态同步与发货回传

14. OMS 订单状态枚举很细（0 待审核 / 10 处理中 / 15 清关中 / 20 清关完成 / 30 已下发仓库 / 40 出库 / 70 揽收 / 100 签收 / 50 取消 / 80-81 撤单 / 90-91 退货入区），与前端 4 态的映射建议：
    - `ship 待发货` = 已支付 ~ 已打单（10/15/20/30/35）
    - `recv 待收货` = 出库 ~ 揽收（40/70）
    - `done 已完成` = 签收（100）
    - `已取消` = 50/80/81（前端需补这个态，原型目前没有）
    - 90/91 退货入区 → 归入售后流程（短期人工）
15. **没有主动推送（发货回传除外）→ 状态靠轮询**：用 `updateTimeStart/End` 增量轮询 `jm.order.bonded.get`，后端定时任务（NestJS Schedule），轮询频率与分页（每页上限 200）写进 oms-adapter 设计。
16. **发货回传（君梦 → 我方）**：我方需提供公网 HTTPS 回调 URL；回传带 `sign + appId`，**我们必须验签**，但文档没写回传的签名规则（签哪些字段、是否同一套 MD5 规则）——待确认。回调入口还要做幂等（同一物流单号重复推）。
17. 查询返回里 `consignee` 是**密文** → 订单详情页的收货人展示用我们自己库里的数据，别指望 OMS 回显。
18. 商品/库存的**按时间增量同步「目前暂不支持」** → 只能全量分页拉或按编码点查。库存策略建议：本地缓存 + 定时全量同步 + 下单前实时点查 `jm.inventory.get` 校验 `availableNum`。
19. 售后接口 `jm.aftersale.bonded.get` 标注「开发中」→ 退款/售后短期只能人工处理，产品设计上别承诺线上售后。
