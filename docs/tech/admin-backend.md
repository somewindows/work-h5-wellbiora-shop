# 后台管理系统设计（运营自助更新）

> 阶段 B 技术设计文档。回应的核心诉求：**产品、首页等内容更新要方便，不找开发、不发版。**
> 数据形态已定稿见 content-blocks.md——后台本质上就是内容块数组和商品档案的可视化编辑器。

## 一、定位与原则

- 服务对象：1~3 人的运营/管理员团队，不是多租户 SaaS，**权限从简**（管理员一个角色起步）。
- 原则：能表单就不 JSON，能开关就不改码；但**不为「可视化拖拽装修」过度投入**——4 个 SKU 的规模，排序+表单足够。
- 与 H5 商城共用同一个 NestJS 服务和数据库，后台只是另一组 `/admin/api` 接口 + 独立前端工程。

## 二、技术形态

- `admin/`（待建）：Vue 3 + Vite + TS + **Element Plus**（桌面端管理后台，不用 Vant——那是移动端的）。
- 部署：与 server 同机，Nginx 挂 `/admin/` 路径，IP 白名单或强密码 + 验证码，不对公网搜索引擎暴露。
- 所有写操作记操作日志（谁、何时、改了什么、改前改后值）。

## 三、功能模块（按优先级）

### P0 — 没有就不能上线
1. **商品管理**：基础信息（名称/英文名/规格/主题色/卡片图/标签）、价格（分）、上下架开关、关联仓库 `goods_no` 与 `warehouseCode`。
2. **详情页内容编辑**：内容块列表编辑器——块卡片可排序/增删/禁用，按 type 出表单（图片块接素材库选择器，营养表给行列表格编辑器）；草稿/发布双态 + 上一版回滚（机制见 content-blocks.md 第四节）。
3. **订单管理**：列表/详情（本地状态+君梦原始状态并排展示）、手动触发状态同步、取消与退款操作（带二次确认和窗口校验）、海关退单（systemRemark）醒目标记。
4. **登录与权限**：管理员账号密码登录，操作日志查看。

### P1 — 上线后很快会要
5. **首页配置**：首页内容块数组编辑（同详情页编辑器复用），hero 图、产品宫格选品与排序。
6. **素材库**：图片上传（对象存储+CDN）、按商品归档、未引用图片提示（原型打包时「排除未引用图片」就是手动干的这事，后台应自动化）。
7. **库存看板**：只读展示君梦库存（jm.inventory.get 定时同步），低库存告警线配置。
8. **合规文案管理**：合规声明固定文案、协议正文（用户协议/隐私政策）的编辑——改文案留版本记录。

### P2 — 有闲再做
9. 数据看板（订单量/GMV/转化漏斗）
10. 客服备注、退款审批流
11. 内容块可视化预览（H5 页 iframe 实时预览草稿）

## 四、典型运营操作的路径（设计自检）

| 运营想干的事 | 路径 | 要发版吗 |
|---|---|---|
| 改某产品价格 | 商品管理 → 编辑 → 保存 | 否 |
| 详情页换一张图 | 详情编辑 → 点图片块 → 素材库换图 → 发布 | 否 |
| 详情页加一段文字 | 详情编辑 → 添加 text 块 → 发布 | 否 |
| 首页换 hero 图/调产品顺序 | 首页配置 → 编辑 → 发布 | 否 |
| 上架第 5 款产品 | 商品管理新建 → 配内容块 → 关联 goods_no → 上架 | 否 |
| 加一种**新的块类型**（如视频块） | 要先走 content-blocks.md 的「登记 type → 写渲染组件」流程 | **是**（前端发版） |

最后一条是唯一需要开发介入的场景，这是内容块架构的固有边界，提前说清楚。

## 五、防呆与红线

- 发布前服务端校验：块 type 合法、必填字段齐、图片 URL 可达、**宣称数据带 `*` 必须有脚注来源**（合规红线，校验不过禁止发布）。
- 合规声明块不出现在编辑器里（系统固定注入），后台只能改文案，且改动需二次确认。
- 价格改动即时生效但记日志；正在结算的订单以 `orders/precheck` 时的快照价为准，不受改价影响。
