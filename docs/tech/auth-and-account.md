# 登录与账号体系方案（H5-shop）

> 决策日期：2026-08-26（已与项目负责人确认）。本文是登录/账号体系的**单点事实源**，后续有改动直接更新本文。
> 原型落点：`prototype/app/login.html`（手机号验证码免密）；入口：`mine.html` 未登录态「立即登录」。

## 一、结论（已定方案）

- **账号主键 = 手机号，短信验证码免密登录**：不设密码、没有「找回密码」流程。新用户首次验证手机号即自动注册。
- **微信内浏览器**：走 `snsapi_base` 网页静默授权拿 openid 做**免登体验层**——openid 已绑定账号则直接免登进入；未绑定则引导「手机号 + 验证码」注册，注册成功的同时把 openid 与账号绑定，下次免登。
- **微信外浏览器**（系统浏览器、其他 App 内 WebView）：只有「手机号 + 验证码」一条路。
- **实名（姓名 + 身份证）不在注册环节采集**，保持在下单/地址环节收（仅用于海关清关），与结算页/地址页现状一致。

## 二、关键事实（不要再踩认知坑）

1. **H5 网页没有「微信一键登录」**：一键登录（手机号快速验证）是 App/小程序的能力，网页不存在。
2. **`snsapi_base` 只能拿 openid**：不弹授权框、拿不到昵称头像手机号，只能用于「认出这个人」；要用户信息需 `snsapi_userinfo`（弹框，体验差，不用）。
3. **网页授权只在微信内有效**：微信外打开同一 URL 无法走 oauth2 授权流程，所以短信验证码通道必须长期保留，不是过渡方案。
4. openid 按公众号维度隔离：同一个用户在不同公众号下 openid 不同；若未来有小程序/App，需绑定微信开放平台拿 **unionid** 做跨端统一（先预留字段）。

## 三、坑清单（实施时逐条对照）

1. **公众号要求**：网页授权（snsapi_base）需要**已认证的微信服务号**；订阅号/未认证服务号没有这个接口权限。
2. **授权回调域名只能配一个**（公众号后台「网页授权域名」）：测试环境和生产环境不能共用同一个服务号的回调域名——要么准备两个服务号，要么测试环境用测试号（接口权限齐全但模板消息等受限）。
3. **微信外投放必须留短信通道**：抖音/小红书/短信营销等微信外渠道引流进来的用户只能手机号登录，别做「仅微信登录」的假设。
4. **短信防刷**：图形验证码/滑块前置、单手机号 + 单 IP 频次限制、验证码 5 分钟有效且限次试错——短信是实打实的成本，上线前必做。
5. **合规勾选**：登录页协议勾选（用户服务协议 + 隐私政策）**默认不勾选**、登录前强制校验（原型已实现）；**账号注销渠道**必须有，短期走人工客服（隐私政策已写明）。
6. **登录态存 localStorage，勿依赖 cookie**：微信内 WebView 的 cookie 策略不稳定（第三方 cookie 限制、清缓存行为不同），token 放 localStorage + 请求头携带。
7. **登录后的购物车合并**：游客态加购（本地）→ 登录后合并到服务端购物车，合并规则（同 SKU 数量相加还是取最大、失效商品如何处理）要在 `api-contract.md` 里定义清楚，别让前端各自发挥。
8. **unionid 预留**：用户表现在就留 `unionid` 字段（可空），避免未来接小程序时迁移。
9. **实名 ≠ 注册**：注册只收手机号；姓名+身份证在下单环节收、仅用于清关——两条数据链路别合并，隐私政策里也是这么承诺的。
